这份清单记录代码里**已经发现**的隐患与边界情况。用法：

- 每次做代码审查，新发现的开到对应档次；修好的挪进"已修"并注明提交
- **一档**：用户看得出来，或者会改坏数据——优先级最高
- **二档**：边界与体验问题，通常顺手就能修
- **三档**：已知的取舍，或者要等对应功能做出来才好定的设计问题

## 二档

**1. 未加入目标文件夹的素材照片也能进入编辑状态**

- 在大图里选中一张还没加入目标文件夹的素材照片后，旋转 / 翻转 / 裁切仍会记录在中间商里，
  但保存计划只包含目标序列中的照片，因此这份编辑不会写到磁盘。
- 目前不会丢原文件；只是 `isDirty()` 会提示有未保存改动，关闭时选“保存”可能得到
  “没有可以保存的改动”的提示。后续应限制编辑入口，或在加入目标文件夹后再允许编辑。

**2. 保存失败后的回滚是尽力而为，不是完整事务**

- 已保证不会因为后续失败而永久删除垃圾桶文件，并会把未被占用的改名临时文件放回原名；
  但已经成功复制 / 改名 / 重写的部分不会自动撤销。保存器返回问题清单，界面会保留失败项。
- 真正的“全有或全无”需要保存计划日志和崩溃恢复机制，目前仍按文件操作逐步执行。

## 三档

**1. 勾选父文件夹不会影响子文件夹**

- 现在只列根目录的直接子文件夹，语义范围还很清楚。
- 等分组做出来、用户能勾更深的层级时，必须一起定义"勾父是否连带子"。

**2. 单个文件夹里几千个文件时，素材条会排成几万像素的长条**

- 虚拟化只画可见的十几格，所以还能撑住；但 `000_成片C` 那种上万文件的地方，真正好用的方式是按子文件夹切成组。
- 分组做出来之后缓解了一部分：把根目录选到 `000_成片C` 这一层，它下面的日期文件夹就各自成组了。但单个文件夹内部仍然是长条。

**3. ICC 色彩配置被忽略**

- 现象：广色域照片（Adobe RGB、Display P3）显示会偏色。
- 处理方向：要做真正的色彩管理得引入相应支持，先记着。

**4. 全程没有日志**

- 现象：`ThumbnailService` 写缓存失败是静默吞掉的（有意为之，缓存失败不该影响功能），但连一行记录都没有，出问题无从查起。
- 处理方向：先定"日志往哪写、用什么方式"，再统一加。

**5. 保存中断残留能被发现，但还不能自动恢复原文件名**

- 启动和切换目标目录时会检测 `__renaming_` / `__trashed_` 等残留，
  它们不会再被当成正常照片，并会弹窗提示。
- 由于临时名本身不携带最终编号映射，目前不能安全地自动还原，需要人工确认后处理。
- 处理方向：保存开始时写一份计划清单，崩溃后按清单恢复。

**6. 编辑后的照片同时占两份全尺寸内存**

- 没有编辑时 `image` 与 `rawImage` 是同一对象；一旋转就多出一份全尺寸结果。
- 高像素照片上可能额外占用数十到上百 MB，后续做大图缓存时要一并考虑。

**7. 已经开始的旧缩略图解码无法中途停止**

- 换目录后，还在队列里的任务会在真正解码前被跳过；但已经进入 `ImageIO` 的那几张
  仍会跑完，只是结果会被丢弃。只浪费 CPU，不影响正确性。
