# 摄影集照片筛选器 · 软件设计

版本 v0.1 ｜ 2026-10-16 ｜ 配合《需求分析》阅读

## 1. 界面结构

界面有两个状态，由目标文件夹面板头部的「展开 / 收起」按钮切换。

```
【浏览模式】按下「展开」之前

┌──────────┬───────────────────────────────┬──────────────────┐
│ 目录树    │ 素材照片信息 ｜ 缩放            │ 目标文件夹   ▾    │
│          ├───────────────────────────────┤ （小缩略图网格）   │
│ ▾ 照片_    │                               │                  │
│   Leica_  │        素  材  大  图          │  头部有「展开」按钮 │
│   M10     │                               │                  │
│   ▸ 095_  │                               │                  │
├──────────┴───────────────────────────────┴──────────────────┤
│ ▾ 095_2026_0929 [□][□][□]  ▾ 096_2026_1001 [□][□][□] ← 素材照片│
└─────────────────────────────────────────────────────────────┘

【整理模式】按下「展开」之后

┌──────────┬───────────────────────────────┬──────────────────┐
│ 目录树    │ 目标文件夹的基本信息            │                   │
│          ├───────────────────────────────┤      垃圾桶        │
│          │ 目标文件夹的缩略图（更大）       │                   │
│          │ 可拖动排序，白线标记落点          │  ← 分隔条可左右拖动 │
├──────────┴───────────────────────────────┴──────────────────┤
│ 目标文件夹的照片  ← 横向滚动                                   │
└─────────────────────────────────────────────────────────────┘
```

| 区域 | 浏览模式（收起） | 整理模式（展开） |
| --- | --- | --- |
| 顶部 | 菜单栏（文件/编辑/图像/查看）+ 快捷工具栏，详见下方小节 | 同左 |
| 左栏 | 素材目录树：根目录 → 子文件夹 → 子文件 | 同左 |
| 中栏上方 | 素材照片信息：文件名 · 路径 · 像素 ｜ 缩放 | 目标文件夹的基本信息 |
| 中栏 | 素材大图，方向键连续过片 | 目标文件夹的缩略图，更大，可拖动排序 |
| 右栏 | 目标文件夹的小缩略图网格，头部有「展开」按钮 | 垃圾桶 |

缩略图格子按**方框**留位（横竖都放得下）：横照片（3:2）满宽显示，
竖照片（2:3）也占满一格宽度、竖着立起来，而不是缩成中间一条窄条。
「查看 → 缩略图大小」改的是一格的宽度，高度跟着按这个比例算。

目标文件夹里的照片可以直接**拖着换位置**：拖动时一张缩略图跟着鼠标走、
落点用白线标出，松手就插到那里，编号跟着位置现算。
提示缩略图由**正在拖动的那块网格**提供；选图模式和整理模式各用各的缩略图，
不从另一块已经隐藏的面板借用，否则会把灰块或旧图拖出来。
落点是"插在某一项之前"的视觉槽位——把第 0 张拖到第 3 个缝里，
意思就是"挪完之后排在原来那三张的后面"（`Session.move` 的目标位置会相应减一）。
| 底栏 | 素材照片，按子文件夹分组，每组可收起 | 目标文件夹的照片 |

交互要点：

- 左栏**双击某个文件夹**，底部的素材照片条同步跳转到那一组
- 右栏与中栏之间的**分隔条可以左右拖动**，自己分配宽度
- 整理模式下拖动照片排序，落点用**白线**标出，插入完成后编号才重算
- 垃圾桶里的照片可以**拖回**序列，落点同样用白线标出
- **选图模式下，把目标栏的照片拖到中间的大图区 = 丢垃圾桶**（大图区会亮一圈白边示意）。
  这只是从序列里摘出来、在垃圾桶里记一个指针；保存时才真删，关程序选"不保存"就当没发生

### 顶部菜单与快捷工具栏（参照 Capture One）

菜单栏：**文件 / 编辑 / 图像 / 查看**，条目参照 Capture One 对应菜单裁剪。

快捷工具栏分三组，组与组之间拉开距离，组内图标紧凑排列：

| 分组 | 内容 |
| --- | --- |
| 左 · 文件与历史 | 重新选择工作区（对应 C1「导入」的位置）、保存（对应「导出」的位置）、重置（清空当前这张照片的全部修改）、撤销 / 重做 |
| 中 · 光标工具 | 选择、平移、裁切、旋转、翻转，连成一排，每个带下拉小三角 |
| 右 · 视图辅助 | 网格、适应窗口、双视图切换（浏览 / 整理） |

视觉规范（自截图取样）：

- 图标为浅灰线性图标，**图标下方带小字标签**，与 Capture One 一致
- 中间的「光标工具」是一整条紧凑连排的工具带，当前激活的那个用暖橙色高亮
- 激活色实测 `#FF8B16`；工具栏底色照旧 `#2D2D2D`

图像编辑的语义（已确认）：**裁切 / 旋转 / 翻转只影响当前查看**，
作为虚拟编辑记在中间商里；保存时才真正落实到 JPG 文件上。
「重置」= 把**当前这张照片的所有修改清空**（旋转 / 翻转 / 裁切），还原成未经编辑的原始状态。

### 旋转与翻转（第一批落地的编辑）

- 工具栏上的「旋转 / 翻转」是**点一下马上生效**的动作型工具：选中它的同时也对当前这张做一次，
  再点一次就再做一次。点「选择 / 平移」或从「图像」菜单操作之后，工具会拨回"选择"。
- 功能按钮**不改变鼠标形状**：鼠标始终使用系统默认箭头；
  只有真正按住「平移」拖动画面时，才临时显示系统的移动光标。
- 编辑状态写成 `EditState`：**先顺时针转 n 个 90°，再按需上下翻**。
  这是八种方向的唯一写法——左右翻记成"转 180° + 上下翻"，所以连续翻转不会越记越乱。
- 画面每次都是从**原图**重算（`PhotoTransforms.apply`），不在上一版结果上叠：
  避免多次重采样发糊，撤销时也能干净地还原。保存时烧进 JPG 会复用同一个方法，
  保证"屏幕上看到的"和"存下来的"是同一张。
- **裁切**用相对坐标 `CropRect` 记在 `EditState` 里。裁切工具显示未裁切的完整画面，
  框选后立刻提交；之后再旋转 / 镜像时选框会跟着做坐标变换，不会跑到另一块区域。
  裁切和旋转 / 翻转共用撤销、重置、保存重写同一条链路。
- **网格**是查看辅助，不在 `EditState` 里：工具栏按钮只切换三分线叠加，不保存、不参与撤销。

### 键盘快捷键

全部集中在 `MainPanel` 顶部的快捷键表里，改键只改那一处。

| 键 | 动作 |
| --- | --- |
| 空格 / 回车 | 把素材条里当前这张**追加到目标序列末尾** |
| Ctrl+Z | 撤销上一步（挑入 / 挪位 / 丢垃圾桶都算） |
| ← / → | 上下一张（跨组连续，走到组尾自动进下一组） |
| Ctrl+S | 保存 |
| Ctrl+O | 重新选择工作区 |
| Ctrl+Q | 退出 |

「查看 → 默认缩放」：每张照片默认“适应窗口”，也可以改成固定百分比；档位中包含 16%。
4:6 画幅（如 4000×6000）在 720×1080 有效查看区里的适应结果正好是 16%：
理论贴合比例上再留出 2 个百分点，避免图片顶满窗口。
和「查看 → 缩放」是两回事——那个管"眼前这一张多大"，这个管"以后每张多大"。
选了之后当前这张立刻按新倍率显示，并记进
`%APPDATA%\PhotoSelector\preferences.properties`，下次打开还是它。

## 2. 分层与包结构

```
com.photoselector
├── app    启动与依赖装配
├── core   领域模型：Photo / PhotoGroup / Session（中间商） / NumberingRule / UndoStack
├── io     文件与图像访问：ImageSource、缩略图与缓存、保存器、文件夹监听
└── ui     Swing 界面
```

**约束：`core` 与 `io` 不得 import 任何 Swing 类。**

这不是洁癖，有两个实际收益：挑选逻辑、编号规则、目标序列这些都能脱离界面写单元测试；
以后即使更换界面框架，业务逻辑也不需要改动。

## 3. 核心域模型

### 3.1 Photo（不可变）

描述一张源照片：源文件路径、所属组、像素宽高、类型（JPG / DNG）。
不可变意味着它一旦创建就不会被修改，所有状态变化都发生在别处，便于推理和测试。

### 3.2 PhotoGroup

一个子文件夹 = 一个组。持有该组的照片列表和折叠状态。
胶片条上每个可收起的框就是一个 `PhotoGroup`。

### 3.3 两层模型：虚拟的中间商 与 真实文件

设计上要始终分清两层，它们是两回事：

| | 抽象层（程序里） | 具体层（电脑里） |
| --- | --- | --- |
| 是什么 | 一个虚拟的「中间商」对象 | 磁盘上的真实文件 |
| 何时变化 | 用户每一步操作都立即改变它 | 只在「保存」或关闭程序时被写入 |
| 存在形式 | 纯内存状态，程序退出即消失 | 真实存在，任何程序都看得到 |

**中间商**（代码里叫 `Session`）记住三样东西：

- 目标序列：有序的条目列表。每条记录它「将来叫什么名字」和「内容来自哪里」——
  来源只有两种：指向目标文件夹里的真实文件，或指向素材文件夹里的文件（还没复制）
- 每条条目还可以带一组**未保存的图像编辑**（旋转 / 翻转 / 裁切）
- 垃圾桶：被移除条目的**引用清单**——里面放的是指针，不是文件；
  指针还能再拖回序列，效果等于撤销这一步移除
- 所有界面操作（挑入、排序、拖进垃圾桶、撤销）只修改这个内存对象

**保存**（按「保存」按钮或关闭程序时）才动磁盘。
保存 = 把中间商与磁盘现状做一次对比，执行最小差异：

| 中间商里的变化 | 落到磁盘的动作 |
| --- | --- |
| 新挑入的照片（来源是素材） | 复制进目标文件夹，按新编号命名 |
| 序列顺序变了 | 按新编号重命名受影响的文件 |
| 条目带了未保存的图像编辑 | 按编辑结果重新编码写回 JPG |
| 垃圾桶里有「真实文件」条目 | 永久删除该文件 |
| 垃圾桶里有「尚未复制」的条目 | 什么都不做——它只是一条引用，从来没有过文件 |

一个推论要特别说清楚：**把一个真实文件拖进垃圾桶之后，在按保存之前，磁盘上它一直都在**，
只有保存那一刻它才离开目标文件夹。若关闭程序时选择不保存，
整场会话的所有改动（包括垃圾桶里的移除）全部作废，磁盘保持原样。

图像编辑同理：浏览时转个方向、裁一刀，都只是中间商里的一份记录，
原文件纹丝不动；保存时才重写 JPG。代价是 JPG 会被**再压缩一次**，
这是有损的，所以采取的办法是：**只对真正动过编辑的照片重写，没动过的原样复制**。

把照片拖回序列时按落点插入（和排序同一套白线规则）；
想回到"原来第几位"则用撤销，那是撤销栈的职责。

关闭程序时的处理，以及**换工作区**之前：询问「是否保存？」。保存则先执行上面的最小差异再继续；
不保存则直接继续，中间商连同垃圾桶一起消失——这正是「关闭程序时垃圾桶清空」的
精确含义：清空的是内存里的引用，不是删除文件。

### 3.4 状态与撤销

素材照片只有两种状态：**未处理** 和 **已加入目标序列**，
以中间商的目标序列里有没有它为准。

这里没有"排除"这个概念：素材文件从头到尾不会被修改，
所以对它的任何标记都只是临时的显示辅助，不值得做成一套体系。

撤销在这个模型里变得特别简单：所有操作都只是对内存对象的修改，
撤销栈记录反向操作、直接改回内存状态即可——**撤销本身不碰磁盘**。
真正碰磁盘的只有「保存」这一个动作（见第 8 节）。

### 3.5 编号规则（可配置）

`NumberingRule` 持有三个参数：起始值、步进、名字格式串（`%d` 替换成编号值）。
默认 `起始 10 / 步进 10 / 格式 "0%d"`，即第 1 项 `010`、第 2 项 `020`、第 23 项 `0230`。
用格式串而不是"补零位数"，是因为这种"前后各一个 0"的形状并非固定宽度，数位会随编号自然增长。

> **已知且不打算处理**：这种编号按文件名排序时顺序会乱——`0100`（第 10 张）
> 会排在 `020`（第 2 张）前面，`090` 又排在 `0100` 前面。实际使用不依赖文件名排序
> （在程序里按位置浏览、按顺序导出），所以保持现状。
> 真要改，把格式串换成 `"%04d"` 即可，不用动代码。

## 4. 工作区与启动流程

### 4.1 一条原则

磁盘是唯一的事实来源。工作区配置记录「你选了什么」；
中间商是磁盘快照加上本次会话未保存的改动；保存时把改动写回磁盘。
无论程序是否正在运行、是否中途崩溃，磁盘上的内容始终自洽。

### 4.2 启动流程

```
启动
 │
 ├─ 读取上次的工作区配置
 │
 ├─ 没有配置 ──> 打开「选择工作区」界面
 │                 · 选素材根文件夹
 │                 · 在树下打勾，决定哪些子文件夹纳入范围
 │                 · 选目标文件夹
 │                 · 确认后进入主界面
 │
 └─ 有配置 ──> 直接进主界面，但先与磁盘对账：
                 素材根目录不存在     → 退回「选择工作区」并说明原因
                 某条剔除项不存在     → 忽略该项，其余照常
                 目标文件夹不存在     → 提示后要求重新选择
                 目标文件夹内容有增减 → 以磁盘实际内容为准重建快照
                 上次会话未保存的改动 → 不恢复，磁盘现状即起点
```

### 4.3 配置存放位置

`%APPDATA%\PhotoSelector\workspace.properties`，用 JDK 自带的 `java.util.Properties` 读写。

选它的理由：不引入任何依赖；文件是纯文本，你可以直接打开看里面记了什么，出问题也好排查。

### 4.4 「选择工作区」界面

- 与主界面左栏共用同一套「目录树 + 打勾」组件，不重复实现两遍
- 顶部工具栏提供「重新选择工作区」入口，打开的是同一个界面
- 更换目标文件夹：先把当前改动保存到旧文件夹，然后中间商清空，开始为新文件夹服务

### 4.5 运行期间的外部修改

程序运行期间，用户可能用资源管理器等外部工具改动目标文件夹。
抽象层必须立即跟进——磁盘是事实来源，事实变了，中间商马上改。

实现：用 JDK 自带的 `WatchService` 监听目标文件夹。事件先去抖
（约 300 毫秒内的一串事件合并成一次处理），然后重新列出磁盘文件与中间商核对。

| 外部发生的事 | 中间商的响应 |
| --- | --- |
| 删除了某张照片 | 该条目从目标序列消失，后面的编号顺延重算 |
| 新增了某张照片 | 没有未保存改动时按磁盘顺序重置；有改动时追加到当前序列末尾，不打乱用户排序 |
| 改了名 | 旧条目消失、新条目按新名字出现 |
| 动了垃圾桶指向的文件 | 该指针作废，从垃圾桶里拿掉 |
| 动了「还没保存」条目的来源文件 | 保存时提示并跳过该条 |

两条实现要点：

- **去抖**。一次改名会触发一连串事件，去抖保证一串事件只对账一次，
  避免反复重扫大文件夹。
- **保存期间延后对账**。保存动作本身也会触发事件；保存期间只记一笔，
  收尾后再对一次账，不让自己引发的事件造成循环重扫。
- **目录失效后恢复**。目标目录被删除或改名时，监听键会失效；监听器先通知上层，
  再等待同一路径重新出现，并自动重新注册。

同样的机制以后可以直接套用到素材文件夹，第一版先只监听目标文件夹。

## 5. 图像来源抽象 —— DNG 之所以能"往后放"

```java
public interface ImageSource {
    String fileName();
    int width();
    int height();
    BufferedImage loadFull();               // 大图视图使用
    BufferedImage loadThumbnail(int height); // 胶片条与右栏使用
}
```

第一版只实现 `JpegImageSource`（`ImageIO` 直接读取）。
以后新增 `DngImageSource`（解析 TIFF 的 IFD 链表、取出内嵌的全尺寸 JPEG 预览），
**界面层一行都不用改**。这是"先不做 DNG"能成立的技术前提。

## 6. 线程模型

Swing 有两条铁律，必须从一开始就守住：

1. 所有界面改动只能在事件分发线程（EDT）上做
2. 读文件、解码、缩放这些耗时的活，绝不能放在 EDT 上

```
EDT（界面线程）                后台线程池（CPU 核数 - 1）
     │                               │
     │  请求缩略图 ─────────────────>  读文件 → 解码 → 缩放
     │                               │
     │  <───── SwingUtilities.invokeLater 回传结果
     │  更新界面
```

在此之上加**预取**：当前看第 N 张时，后台已经把 N+1、N+2 张解码好了，翻页就是瞬时的。

## 7. 缓存与渲染性能

缩略图缓存分两层：

- 内存：固定容量的 LRU，存放最近用过的几百张
- 磁盘：缩略图文件，键 = 文件路径 + 文件大小 + 最后修改时间

两个具体的性能要点：

- **胶片条自绘**。一个组可能有 313 张，如果给每张都放一个 `JLabel`，
  Swing 要维护几百个组件。正确做法是重写 `paintComponent`，只绘制当前可见范围内的缩略图。
- **目录树懒加载**。展开某个文件夹节点时才去读它的子项，避免启动时扫描上万条目录项。

## 8. 保存动作的安全设计

磁盘只在「保存」这一刻被修改，所以安全措施都集中在保存这一步：

1. **关闭时不保存 = 全局撤销**。任何误操作，只要还没按保存，
   都能靠「关闭并选择不保存」全部作废，磁盘毫发无损。
2. **两阶段重命名**。批量重排编号时，先把待改文件统一改成临时名，
   再改成最终名，避免 A 改 B、B 改 A 的互相覆盖。
3. **源素材只读**。素材文件夹里的文件永远只被读取，不移动、不删除。
4. **重名不静默覆盖**。复制进目标文件夹时若已存在同名文件，先问，不自作主张。
5. **没动过的不重写**。只有真正带着图像编辑的照片才重新编码写回 JPG，
   其余原样复制，避免无谓的画质损失。
6. **复制先写临时文件**。成功后再原子改成最终编号，失败会清掉临时文件，
   不会把半截 JPG 当成保存成功。
7. **重写照片保留元数据**。新 JPG 写完后，把原文件的 EXIF / XMP / ICC / IPTC
   等 APPn 段原样带回；EXIF 与 XMP 里的旧方向统一改成 1，因为像素已经摆正。
   APP14、MPF 这类绑定旧编码结构的段明确跳过，避免颜色变换或多图偏移失效。
   EXIF 的像素宽高同步成输出尺寸，旧 IFD1 内嵌缩略图从链上断开。

按设计决定：保存时对垃圾桶里真实文件的删除是**永久删除**，不进系统回收站——
这是「垃圾桶只存指针、不要双保险」的直接推论，唯一的后悔药是「不保存地关闭」。

### 关窗口的流程（点 × 与菜单「退出」同一条路）

1. 中间商没改动 → 直接退出。
2. 有改动 → 问一句「保存 / 不保存 / 取消」。
3. 选保存 → **等保存真的跑完再退**（保存是后台线程干的活，问完就跑等于中途撤人）。
4. 选不保存 → 立刻退出，磁盘保持原样，中间商连同垃圾桶一起消失。
5. 把对话框直接关掉 → 当作取消，程序留着。
6. 保存有失败 → **不退出 / 不切工作区**，弹报告并保留中间商，等用户处理磁盘问题后重试。

「有没有改动」由中间商当前状态和“上次与磁盘对齐时的快照”比较得出。
因此撤销回原样后会自动恢复为干净状态，不会再多问一次“要不要保存”。

## 9. 界面组件库

`ui/theme` 是整个界面共用的"库"，规矩只在这里定一次：

| 文件 | 管什么 |
| --- | --- |
| `Theme` | 配色、字体、控件外观（`UIManager`）、滚动条 |
| `Icons` | 全部按钮图标的画法（18×18 设计稿） |
| `TextStyles` | 文字截断：`end`（保留开头）/ `middle`（保留盘符与尾部） |
| `Painters` | 画笔集：选中亮底、占位框、缩略图等比居中、胶囊按钮、标题栏、落点白线、空状态提示 |
| `ChipGroup` | 一组胶囊按钮的右对齐布局；绘制矩形和命中矩形共用同一份几何 |
| `ThumbnailGridPanel` | **缩略图网格基类**：留白 / 列数 / 虚拟化 / 取图 / 落点白线一套全包；子类只填"数据从哪来"和"每格画什么" |

目标栏（`TargetPanel`）和垃圾桶（`TrashPanel`）都继承 `ThumbnailGridPanel`，
各自只剩几十行差异代码。素材条（`FilmstripPanel`）**不**继承它——它是横向、按组、可折叠的，
布局规律和竖网格不是一回事，硬套只会把基类拧成两套逻辑。

模板方法就四个：`itemCount()`、`sourceAt()`、`paintCellContent()`、`paintEmptyHint()`，
外加可选的表头点击 / 格子点击回调。基类不认得 `Session`——`FakeGrid` 测试里
用一个纯列表就能把它跑起来，证明没有偷偷绑死在某块面板上。

几条**不成文的规矩**，都写进了 `Painters` 的注释里：

- 选中一格用"外扩 2 像素的亮底"，不用 1 像素描边——缩放显示下描边宽度不稳
- 照片区不铺底色，直接露出面板的深灰；占位只画一圈暗边框
- 缩略图一律等比缩进格子、居中，宁可留白也不裁切
- 胶囊按钮的三种状态（激活 / 悬停 / 普通）统一由 `Painters.chip` 画

验证靠两张"验货图"，它们由测试随手生成，永远是当前代码的真实样子：

- `target/ui-icons.png`：每个工具的按钮图标总览
- `target/ui-component-library.png`：胶囊按钮、缩略图格子、文字截断、落点线的总览

这不是一套通用控件框架，而是本项目自己的样式层——面板的绘制需求差异太大
（横向分组 / 网格 / 原编号 / 缩放平移），硬抽基类只会多绕几道弯。
