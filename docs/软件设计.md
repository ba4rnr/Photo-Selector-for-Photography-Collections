## 1. 界面结构

```

├──────────┬──────────────────────────────────────┬─────────────────┤
│ 目录树    │ 文件名 · 路径 · 像素      │  缩放   │ 目标文件夹  ▾    │
│          ├──────────────────────────────────────┤                 │
│ ▾ 照片_    │                                      │ 导出后目标文件夹 │
```

| 区域 | 内容 | 关键交互 |
| --- | --- | --- |
| 顶部 | 菜单栏 + 快捷工具栏 | 重新选择工作区（素材 / 剔除 / 目标）、导出、撤销/重做、缩放 |
| 左栏 | 目录树：根目录 → 子文件夹 → 子文件 | 单击选中；**双击文件夹，底部胶片条同步跳转到该组**；勾选框控制是否纳入范围 |
| 中栏上方 | 信息格 + 缩放栏 | 文件名、完整路径、像素；适应窗口 / 100% / 百分比 |
| 中栏 | 大图视图 | 左右方向键连续过片，滚轮缩放 |
| 右栏 | 目标文件夹的「最终状态」预览 | 见 3.3；整栏可收起 |
| 底栏 | 胶片条 | 横向滚动；每个子文件夹是一个组，组带展开/收起按钮 |

## 2. 分层与包结构

```
com.photoselector
├── app    启动与依赖装配
├── core   领域模型：Photo / PhotoGroup / TargetSequence / SelectionModel / NumberingRule
├── io     文件与图像访问：ImageSource、缩略图与缓存、导出器
└── ui     Swing 界面
```

**约束：`core` 与 `io` 不得 import 任何 Swing 类。**

这不是洁癖，有两个实际收益：挑选逻辑、编号规则、目标序列这些都能脱离界面写单元测试；
以后即使更换界面框架，业务逻辑也不需要改动。

## 3. 核心域模型

### 3.1 Photo（不可变）

描述一张源照片：源文件路径、所属组、像素宽高、类型（JPG / DNG）。
不可变意味着它一旦创建就不会被修改，所有状态变化都发生在别处，便于推理和测试。

### 3.2 PhotoGroup

一个子文件夹 = 一个组。持有该组的照片列表和折叠状态。
胶片条上每个可收起的框就是一个 `PhotoGroup`。

### 3.3 TargetSequence —— 本项目最有特色的部分

右栏展示的不是「我选了什么」，而是**「假如现在关掉程序，目标文件夹会是什么样子」**。

把它想成一份待办清单：

- 程序启动时扫描目标文件夹，里面已有的照片构成**基线序列**
- 挑中的照片不立刻复制，而是先进入**计划**，每一条记录自己在序列中的插入位置
- 右栏实时展示「基线序列 + 计划插入项」合并后的最终顺序
- 每一格都按编号规则算出它导出后的文件名，插入一张，后面的号整体顺延

导出时做两件事：

1. 新增的照片按最终编号**复制**进目标文件夹
2. 目标文件夹里受影响的原有文件**重命名**为最终编号

第 2 条是有破坏性的操作，安全设计见第 8 节。

### 3.4 选中状态与撤销

照片本身不可变，选中状态单独放在 `SelectionModel` 中，含三态：未看 / 选中 / 排除。
撤销栈记录「改了哪张、从什么状态改成什么状态」，撤销就是纯粹的数据回放，
不会和界面状态纠缠在一起。

### 3.5 编号规则（可配置）

`NumberingRule` 持有三个参数：起始值、步进、补零位数。
默认 `起始 10 / 步进 10 / 补零 4 位`，即 `0010`、`0020`、`0030` ……

## 4. 工作区与启动流程

### 4.1 一条原则

配置只记录「你选了什么」，画面永远反映「磁盘上真实有什么」。

### 4.2 启动流程

```
启动
 │
 ├─ 读取上次的工作区配置
 │
 ├─ 没有配置 ──> 打开「选择工作区」界面
 │                 · 选素材根文件夹
 │                 · 在树下打勾，决定哪些子文件夹纳入范围
 │                 · 选目标文件夹
 │                 · 确认后进入主界面
 │
 └─ 有配置 ──> 直接进主界面，但先与磁盘对账：
                 素材根目录不存在     → 退回「选择工作区」并说明原因
                 某条剔除项不存在     → 忽略该项，其余照常
                 目标文件夹不存在     → 提示后要求重新选择
                 目标文件夹内容有增减 → 以磁盘实际内容重建基线序列
                 计划里的源文件不存在 → 丢弃该条并提示
```

### 4.3 配置存放位置

`%APPDATA%\PhotoSelector\workspace.properties`，用 JDK 自带的 `java.util.Properties` 读写。

选它的理由：不引入任何依赖；文件是纯文本，你可以直接打开看里面记了什么，出问题也好排查。

### 4.4 「选择工作区」界面

- 与主界面左栏共用同一套「目录树 + 打勾」组件，不重复实现两遍
- 顶部工具栏提供「重新选择工作区」入口，打开的是同一个界面
- 更换目标文件夹时，已有的挑选计划如何处理，见第 9 节

## 5. 图像来源抽象 —— DNG 之所以能"往后放"

```java
public interface ImageSource {
    String fileName();
    int width();
    int height();
    BufferedImage loadFull();               // 大图视图使用
    BufferedImage loadThumbnail(int height); // 胶片条与右栏使用
}
```

第一版只实现 `JpegImageSource`（`ImageIO` 直接读取）。
以后新增 `DngImageSource`（解析 TIFF 的 IFD 链表、取出内嵌的全尺寸 JPEG 预览），
**界面层一行都不用改**。这是"先不做 DNG"能成立的技术前提。

## 6. 线程模型

Swing 有两条铁律，必须从一开始就守住：

1. 所有界面改动只能在事件分发线程（EDT）上做
2. 读文件、解码、缩放这些耗时的活，绝不能放在 EDT 上

```
EDT（界面线程）                后台线程池（CPU 核数 - 1）
     │                               │
     │  请求缩略图 ─────────────────>  读文件 → 解码 → 缩放
     │                               │
     │  <───── SwingUtilities.invokeLater 回传结果
     │  更新界面
```

在此之上加**预取**：当前看第 N 张时，后台已经把 N+1、N+2 张解码好了，翻页就是瞬时的。

## 7. 缓存与渲染性能

缩略图缓存分两层：

- 内存：固定容量的 LRU，存放最近用过的几百张
- 磁盘：缩略图文件，键 = 文件路径 + 文件大小 + 最后修改时间

两个具体的性能要点：

- **胶片条自绘**。一个组可能有 313 张，如果给每张都放一个 `JLabel`，
  Swing 要维护几百个组件。正确做法是重写 `paintComponent`，只绘制当前可见范围内的缩略图。
- **目录树懒加载**。展开某个文件夹节点时才去读它的子项，避免启动时扫描上万条目录项。

## 8. 导出与重编号的安全设计

重命名目标文件夹里已有的照片是有风险的操作，采取三条措施：

1. **两阶段重命名**。先把所有受影响文件改成临时名（如 `__renaming_0001`），
   再统一改成最终名，避免出现 A 改 B、B 改 A 的互相覆盖。
2. **导出前预演**。弹出一份清单，明确列出"将新增哪些、将重命名哪些"，
   用户确认后才真正执行。
3. **源文件只读**。全程只复制、不移动、不删除源照片。

## 9. 待确认事项

1. 左栏目录树里，勾选框的语义是"纳入"还是"剔除"（暂定：勾上即纳入，默认全选）
2. 挑选计划是否需要一并落盘；若需要，按 4.2 的对账规则恢复
3. 更换目标文件夹时，已有的挑选计划是清空，还是保留并改为追加到末尾

### 已确认

- 目标序列支持拖动排序，拖动时用白线标记落点，**插入完成后**才实时重算编号
- 导出时重命名目标文件夹里已有的照片，配三道保护（见第 8 节）
- 启动时无配置则进入「选择工作区」；有配置则恢复，并与磁盘实际内容对账
